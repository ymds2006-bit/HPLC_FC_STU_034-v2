# HPLC Run Decision Tool

Open [index.html](./index.html) in a modern browser and choose a CSV or XLSX exported from a chromatographic run. XLSX conversion uses the SheetJS browser bundle loaded from jsDelivr, so an internet connection is needed for XLSX files.

## Exporting a chat transcript to PDF

Use Node.js and Microsoft Edge or Google Chrome to convert a VS Code Agents `chat.json` export. The PDF is saved beside the JSON file by default, and every page is stamped with `Yenuli DIAS SENEVIRATNE`:

```powershell
node .\convertchattopdf.js .\chat.json
```

You can also pass a second argument to choose the PDF output path:

```powershell
node .\convertchattopdf.js .\chat.json .\chat-transcript.pdf
```

## CSV input

When a CSV/XLSX contains a valid labeled or header-row `%B` value, that extracted value takes precedence over `%B` in the run name and is used as the current method composition for recommendations and the predicted resulting `%B`. If no valid `%B` value is extracted, the parsed run-name value remains the fallback. Other method fields continue to use the existing run-name precedence.

The importer understands LabSolutions CSV exports (including the `[Peak Table(PDA-Ch1)]` and LC status sections) and standard header-row CSV files. It extracts:

- Run-name values are parsed from the CSV/XLSX `Sample Name` in cell B20, using `GR{Group}-{Injection}-{HPLC}-{Solvent}-{pH}-ISO-{%B}-{Flow}-{Volume}[u|uL|µL]-{CP|BLK}[-]{Concentration}-{Ligand}[Column Type]-{Length}x{ID}x{Particle}-{Temperature}-{Wavelength}`. If the Sample Name is missing or cannot be parsed, the uploaded file's name is used as a fallback. Numeric fields are extracted as numbers when the naming convention includes known labels or units, including a `T` prefix on temperature (`T60`), Celsius suffixes, volume suffixes, and an `nm` wavelength suffix. The column type may be attached directly to the ligand (for example, `C18AQP`) or separated by a hyphen (`C18AQ-P`); if omitted, the other method values are still parsed and the app leaves column type and CoreShell unspecified rather than guessing. Sample Volume is shown in its own `Sample Volume (µL)` column; the volume unit is optional in the name, and its parsed value is numeric. Flow, %B, Length, Internal Diameter, Particle Size, Set Temp, Wavelength, and measured temperature are numeric values in the extracted data; `amb`, `ambient`, and `RT` normalize to numeric 25°C. Blank rows are retained when reading CSV/XLSX so B20 remains at its original position. If B20 is blank, the importer falls back to the `Sample Name` label. Group and injection digits retain leading zeroes; Injection No. is the Trial No. `MeOH` normalizes to `METHANOL`; solvent MIX names may contain hyphens; pH and injection volume are variable numeric values. `%B` is restricted to 0–100, temperature to 10–100°C, and wavelength to 190–800 nm. The sample type may be `CP` or `BLK`; a BLK concentration may be omitted. Ligands may contain hyphens, and the token's final letter identifies column type (`P`, `U`, `F`, or `R`) when present. The three column dimensions are Length x Internal Diameter x Particle Size. Pore Size and C-Load are not parsed from the name: they remain editable defaults of 140 and 6, with a visible default-value indicator.
- Parameter values are read from the method name and from exact label/value rows in LabSolutions exports. For simple tabular CSVs, column headers on the first row are also supported. This avoids interpreting later trace-section headings as parameter values.
- For LabSolutions files, the method nomenclature in `Sample Name` is compared with the method name in `Data File Name`. Comparison is case-insensitive and compares parsed values so optional units such as `u` and `nm` do not cause a false mismatch. Different run identifiers or method settings show a mismatch warning in the matching trial's Actions cell. The warning is informational: the parsed Sample Name in B20 continues to supply method values to the decision engine and calculations, while `Data File Name` is used only for comparison. CoreShell is assigned automatically when the column type is known: Raptor is Yes, and other known column types are No; an omitted column type stays unspecified.
- Peak count, total retention time, the lowest positive peak resolution, pressure, and measured temperature.
- Retention times are read from the column titled `R.Time` inside the `[Peak Table…]` section; the parser resolves columns by their header names rather than assuming fixed positions. These exact peak-table values are used for peak retention analysis. Peak data is noise-filtered in memory before analysis: rows with an `Area` below `80,000 AUC` are excluded from calculations, while the uploaded CSV/XLSX is never modified.
- The `Extraction log` panel shows raw and filtered peak counts, each peak's area/threshold/keep decision, and the derived run values. The same information is also written to the browser developer console.
- Back-pressure is calculated from the Pump A pressure trace by averaging every intensity value in its variable-length `R.Time (min), Intensity` table, then multiplying that average by the section's `Intensity Multiplier`.
- The final back-pressure value is rounded and displayed to three decimal places.
- Set Temp is the programmed temperature parsed from the method/file name; `amb` is displayed as 25°C. **An ambient run is defined as a run with Set Temp = 25°C.** Measured Temp does not determine ambient status. Measured Temp is a separate value calculated from the `[LC Status Trace(Oven Temp.)]` section by averaging timestamped temperatures from the trace start (time 0 or the first non-negative timestamp) through the extracted total retention time. The measured average is rounded to two decimal places. If the trace is unavailable, only an explicitly labelled measured-temperature field is used as fallback; Set Temp is not substituted. The Trials table shows separate `Set Temp (°C)` and `Measured Temp (°C)` columns. Suggested rows leave Measured Temp blank because they have not been run. The trace range, sample count, and average are written to the Extraction log. Ambient-run analysis uses Set Temp, not Measured Temp.

Each upload appends one row to the Dashboard. The CSV/XLSX `Data File Name` is parsed only to compare it with the parsed `Sample Name`; it never supplies parameter values. If the `Sample Name` is missing or invalid, the uploaded filename supplies the naming-convention fields instead. When a valid `Sample Name` exists, it remains the source of method values, and an extracted CSV/XLSX `%B` value continues to take precedence over named %B. If the sample and data-file names disagree, or either supplied workbook name cannot be parsed, the row is flagged and its Column & Flow Parameters become editable. Whenever B20 contains a valid method name, all method fields in the parameter table and dashboard come from B20 even when a mismatch warning is shown; conflicting `Data File Name` and labeled fields do not replace those values. Changing them manually remains available only for a flagged row. Pore Size and C-Load remain manually editable at their defaults whether or not there is a naming mismatch. Changing a method specification recalculates all recommendations.

The separate `Current viewed run` panel has been removed; measured values and their color-coded statuses are shown directly in the Trials table. Click any uploaded source-trial row to view that run's Column & Flow Parameters; suggested rows are not selectable source runs. The Column & Flow Parameters table is blank until a run is uploaded. Column Type is parsed from the Sample Name: `P` becomes Pinnacle, `U` becomes Ultra, `F` becomes Force, and `R` becomes Raptor. The detected Column Type is copied to the Trials table and suggested rows. Core-shell is derived from Column Type when known: Raptor is Yes, other known types are No, and an omitted type remains unspecified. Pore Size and C-Load are directly editable defaults for every uploaded run. When the selected trial's Sample Name and Data File Name are inconsistent, the Column & Flow Parameters for that trial are editable; select another source-trial row to view and edit its parameters. Edits update the selected source trial and its suggested rows in the Trials table.

## Equipment tab

The Equipment tab is titled `HPLC Modules Guide` and contains an interactive schematic with clickable regions and tabs for Solvent Bottles, Degasser, Pump, Manual Injector/Autosampler, Column/Column Oven, and Detector. Selecting a module updates its parameter dropdown. Selecting a parameter displays its function, category, instrument control point, units, allowed/typical range, and concise scientific effects on retention, selectivity, efficiency, and system operation. For Pump %B, parameter details identify it as a chemical parameter set and delivered through the pump's mechanical solvent-proportioning system. Its `Decision-engine Relationship` begins with the selected run's pressure, peak count, last-peak retention, and approximate doubled-retention table. When Minimum %B is selected, it also shows the applicable ambient regression-cycle run table, the R²-filtered log10(k)-versus-%B plot and fitted line, and the target-retention calculation using the existing regression result. The Pump view compares binary and quaternary solvent-mixing arrangements, each with its schematic beside the matching instrument photo: binary systems mix after the pumps at high pressure, while quaternary systems proportion solvents before the pump at low pressure. When the Manual Injector/Autosampler module is selected, labeled Manual Injector and Autosampler buttons below the HPLC schematic switch between the corresponding supplied photo. It explains when parameters may be changed and whether the decision engine recommends changing them. The Degasser is identified as a non-adjustable stability module with fault indicators. Instrument-specific limits are identified as such rather than guessed. Reference information is based on the supplied parameter-reference CSV files and is preloaded in the equipment lookup data near the beginning of `app.js`.

For an under-target run, the initial back-pressure pass/fail gate is evaluated first. After it passes, the decision tree evaluates measured peak count and last-peak retention against the method specifications. A `Decrease %B by 10%` decision predicts current %B minus 10 percentage points. Minimum %B keeps its existing course-based regression. Intermediate %B is not calculated from specification scores: when that step is reached, the user inspects the retention-cycle peak comparison, selects or enters a %B, and confirms it. The typical ambient investigation order remains 100, 90, 80, 70, 60, 50, then 40% B, followed by the calculated Minimum %B and user-confirmed Intermediate %B. The prediction follows the branch selected by each run's results rather than advancing through a fixed queue solely because a particular %B was recorded. Once the full ambient 100–40% B sequence and the actual Minimum and confirmed Intermediate runs remain under target, selectivity stages follow. Suggested rows are not evidence of a test: only uploaded results with observed peak count and retention advance a stage. The required next %B appears as a fixed value in the suggested row, except for the ACN-to-MeOH conversion dropdown described below.

Only after the full ambient sequence remains below target does selectivity begin. At the original solvent, test every distinct %B actually run in the immediately preceding completed condition, ordered high to low, at 40°C and then 60°C. Next change solvent and repeat the preceding condition's actual %B sequence at ambient, 40°C, and 60°C; then repeat those stages for MIX; finally test ligands A–D at the final condition's %B sequence. Every stage advances only after all its required actual results are present and under target. If any run reaches target, no further %B/selectivity stage is suggested and the ordinary decision tree handles that run. This ordered investigation is a flowchart path, not an unconditional %B queue: run measurements and method specifications choose the active branch and thus the prediction.

For the ACN-to-MeOH transition, the conversion is **MeOH %B = ACN %B + 10 percentage points**. The Methanol sequence maps the preceding ACN tests through this rule and excludes any mapped value outside 0–100% (for example, 100% ACN → 110% MeOH is not offered). The suggested %B dropdown shows each valid MeOH value alongside its source ACN value and selects the next sequence value by default. The Actions cell identifies the pair as predicted; selecting it opens an interactive two-scale nomogram, with markers that follow the selected dropdown value. Uploaded Methanol runs remain recorded using their actual solvent and measured %B; where a matching ACN source run exists, the Actions cell records and links that source pair. Predicted options never count as completed tests.

Uploaded source-trial records (including their solvent, temperature, ligand, %B and measured peak count, retention time, back-pressure, and resolution where available) are saved in this browser's local storage and restored on reload. Suggested rows are not saved and never count as completed tests. Use `Clear saved runs` to remove the browser's saved run history. If browser storage is unavailable or saved data cannot be read, the interface reports the storage error.

The Dashboard adds a visually distinct suggested next-run row directly below the run that generated the recommendation. Mandatory %B/selectivity suggestions show the required next %B as a fixed value, plus the applicable solvent/temperature/ligand controls. The Decision cell identifies the row as a prediction; it does not claim an outcome before the run is performed. Suggested rows can be deleted, are display-only, are not included in stage-completion checks, and are not included in regression calculations.

Minimum %B remains the course-based retention-factor regression and is shown as its own calculated value; it is not selected by visual inspection. Intermediate %B is an OBSERVE step, not a regression or a ranking of runs by closeness to method specifications. When the decision reaches an intermediate step, the Dashboard displays actual runs from the applicable sequentially decreasing-%B retention cycle side by side, with %B, noise-filtered peak count, last-peak retention, and resolution status. It offers midpoint candidates between adjacent tested %B values only as optional prompts; inspect the peak positions and widths, enter or select a permitted %B, and confirm before the next-run suggestion appears. A candidate is not claimed to improve resolution until measured.

The current importer reads LabSolutions peak-table measurements, not the instrument's raw detector-signal chromatogram. The OBSERVE comparison therefore plots measured retention positions and reported peak widths, not reconstructed chromatograms. Peak labels are elution order within each run, not automated compound tracking. The user must identify critical-pair movement; the app does not automatically select the best intermediate %B. When fewer than seven filtered peaks are present, the observation panel reports `Rs = 0 (not assessable; fewer than 7 peaks)`; otherwise it shows the measured lowest Rs when available.

The minimum `%B` regression uses only the applicable uploaded run series: runs with the same Group No., HPLC No., and solvent as the run being evaluated. An ambient run means **Set Temp = 25°C**. It uses the most recent cycle with successive 10-percentage-point decreases in `%B`, ordered by Injection No.; non-ambient runs and other solvents are excluded. At least three applicable ambient runs with usable data are required for an R²-checked minimum-%B fit; otherwise the tool returns `NA% (Not Enough Runs to Calculate Min %B/Intermediate %B)`. Ligand-name differences do not exclude otherwise matching runs. For each run, noise filtering is applied first: `t0` is the retention time of the first remaining peak, and `tR` is the retention time of the last remaining peak. Those filtered values are used to calculate `k = (tR − t0) / t0` and fit `log10(k) = a × %B + b`. The Extraction log includes a run table with `%B`, filtered `t0`, filtered `tR`, `k`, `log10(k)`, pressure, and fit status. If the fit has `R² < 0.99`, runs are removed one at a time only when the removal improves R², while retaining at least three points. A numeric prediction is returned only if the resulting fit meets `R² ≥ 0.99` and falls within the allowed 0–100% B range. The target retention is the maximum run-time specification; target `k` uses the average filtered `t0` of the retained points: `k = (target retention − average t0) / average t0`. Then target `log10(k)` is substituted into the fitted equation to solve `%B = (log10(k) − b) / a`; the resulting Minimum %B is rounded up to the next whole percentage point. Back-pressure is retained with each extracted run and included in the calculation log.

Optional intermediate-%B candidate values are midpoints between adjacent measured values in the actual sequential retention cycle (for example, 45% between measured 50% and 40% runs). They are only suggestions and are never auto-confirmed. The confirmed user value is stored with the uploaded run history so the next actual upload can be evaluated against the confirmed sequence.

Minimum-%B is recalculated from the applicable run history for each trial that needs a minimum recommendation. Predictions are not frozen or shared between run series. Earlier calculations use only runs uploaded up to that trial; later runs from another Group/HPLC/solvent series cannot alter or supply its regression. Minimum %B requires at least three usable ambient regression points. Intermediate %B is not automatically calculated; it requires a user-observed and confirmed value.

The Dashboard prediction row distinguishes the two minimum/intermediate paths. For `Jump to Minimum %B OR Intermediate %B`, the single predicted row's %B dropdown switches between the calculated Minimum %B and the Intermediate %B confirmed in OBSERVE; its OBSERVE option remains available before confirmation and takes the user to the observation panel. For `Jump to Minimum %B THEN, Intermediate %B`, the first predicted row remains Minimum %B (Step 1). After that actual result is uploaded and OBSERVE confirms an Intermediate %B, a dropdown on the Step 1 row enables adding a separate Step 2 predicted row. That row uses the confirmed Intermediate %B and carries the predicted conditions from Step 1. Intermediate %B is never auto-selected or calculated.

The relevant source and predicted Minimum/Intermediate %B rows link to the Equipment tab's Pump → `%B (Pump composition setting)` relationship. It displays the selected action and predicted %B, the source run's pressure/peak/runtime evidence, the separate Minimum and Intermediate purposes/effects, and the flow rate, column temperature, column/stationary phase, and injection volume held constant. Choosing Minimum %B presents the same regression inputs and fitted points used by the existing calculation; selecting OBSERVE presents the intermediate-composition guidance instead. Intermediate guidance is presented as the requested pump/solvent-delivery → gradient-programme → Intermediate %B link; the existing imported run naming remains isocratic where it identifies `ISO`.

Selectivity source and predicted rows link to the Equipment parameter being tested: Column/Column Oven → Temperature for temperature stages, Solvent Bottles → Solvent Type for ACN-to-MeOH and MeOH-to-Mix stages, and Column/Column Oven → Ligand for the stationary-phase stage. Their Decision-engine Relationship shows measured pressure, peak count and runtime against the active specifications; the planned action and solvent, %B, temperature and ligand; stage purpose and expected chromatographic effects; and a stage-specific table of conditions to hold constant or change. Temperature runs hold solvent, composition, flow, column/stationary phase, injection volume and wavelength constant. Solvent runs describe the configured ACN-to-MeOH percentage mapping or the example 25% ACN/30% MeOH/45% water mix. At each stage, change only the stated variable, update its Equipment parameter, and compare the resulting chromatogram before proceeding.

Equipment decision relationships show PASS/FAIL status badges for back-pressure, peak count and runtime. Expected Chromatographic Effects use concise cause → effect lines. In the Pump guide, `Two Ways to Arrange This` is a collapsed disclosure above the parameter selector; the Minimum/Intermediate choice controls have no CSS minimum width.

For a `Decrease %B by 10%` recommendation the next `%B` subtracts 10 percentage points. Its `Open Decision-engine Relationship` button opens the Pump %B relationship for that run in the Equipment tab. For a minimum-%B recommendation, the regression uses only the applicable Group No./HPLC No./solvent series and its latest sequential cycle of non-suggested ambient runs (Set Temp = 25°C), ordered by Injection No., with each `%B` step decreasing by 10 points. Ligand-name mismatches do not exclude otherwise sequential runs. At least three ambient runs with usable values are required. Noise filtering is applied before selecting `t0` as the first remaining peak's retention and `tR` as the last remaining peak's retention. Each usable run is converted to `K = (tR - t0) / t0`, then fitted as `log10(K) = a × %B + b`. When `R² < 0.99`, a run is removed only if doing so improves R², and at least three points are retained. A prediction is returned only when the resulting regression meets `R² ≥ 0.99` and the result falls within 0–100% B. The average filtered `t0` of the retained runs is used with the configured maximum run-time specification as the target last-peak `tR`; target `K = (target tR - average t0) / average t0`, then target `log10(K)` is substituted to solve `%B = (log10(K) - b) / a`. If fewer than three applicable ambient runs with usable data are available, Minimum %B displays `NA% (Not Enough Runs to Calculate Min %B/Intermediate %B)`. The predicted value is rounded to a whole percent. The Extraction log lists each run's `%B`, filtered `t0`, filtered `tR`, `K`, `log10(K)`, pressure, and fit status, followed by regression coefficients, removed points, average `t0`, target `tR`, target `K`, target `log10(K)`, and R².

The separate visual `Minimum %B calculation` panel has been removed. Minimum-%B calculation details remain available in the Extraction log; predictions are recalculated from each trial's applicable run history.

For runs that meet the target peak count, the provisional “much less than maximum run time” threshold is 50% of the configured maximum. When last-peak retention is below or equal to that threshold and resolution is below the configured Resolution Specification (temporarily used as the floor-resolution threshold), the recommendation is `Increase Length of Column to Increase N`. If retention is above 50% but below the maximum with resolution below specification, the recommendation is `SELECTIVITY`. If retention is below the maximum and resolution meets specification, the recommendation is `MET. increase F until R = spec to get most efficient method`. Above the maximum with resolution below specification, the app resumes the existing staged selectivity plan and suggests the first uncompleted stage (for example, 40°C at the required %B); the sequence stops once both peak-count and resolution targets are met. Above the maximum with resolution meeting specification, the recommendation is `N`. These provisional thresholds are placeholders pending the course-defined time and floor-resolution equations.

For simple header-row files, header matching is case-insensitive and allows common variants of:

- Conditions: `Ligand`, `Column Type`, `CoreShell`, `Pore Size (Å)`, `C Load (%)`, `Length (mm)`, `Ø (mm)`, `PS (µm)`, `Solvent`, `%B`, `Flow (mL/min)`, `Sample Conc (mg/mL)`, `Temp (°C)`, and `Wavelength (nm)`.
- Results: peak count, last peak retention time, resolution/Rs, and back pressure.

If peak count or last-peak retention time is not present, the tool can derive them from rows containing retention times: the number of rows is used as peak count and the largest retention time is used as the last peak. If several resolution values are present, the smallest is used as the worst-separated pair.

## Decision tree

Before any recommendations are generated, the four editable method specifications are centrally validated: target peak count must be a finite positive integer; maximum run time and maximum back-pressure must be finite and greater than zero; minimum resolution must be finite and non-negative. Numeric parsing explicitly rejects empty values, unexpected numeric syntax, and non-finite values. Pressure is entered in psi; there are no separate minimum-pressure or minimum-runtime specification fields, and flow rate is a per-run parameter rather than a decision-engine specification input. No extra scientific limits or cross-field constraints are inferred. Input edits are validated immediately: invalid fields show inline explanations and a prominent warning near the specifications and Trials. Valid edits mark results NOT YET VALIDATED until the user runs analysis. Uploading a file is also an analysis request; while specifications are invalid, the file is not parsed and no recommendation is generated. The `Validate specifications and run analysis` button revalidates all four fields, then recomputes recommendations for already loaded runs and processes any pending upload. While invalid or not yet validated, previous recommendations and suggested rows are cleared/withheld.

The defaults are 7 peaks, 15 minutes, 1.4 Rmin, and 4000 psi. The decision tree uses the retention time of the last noise-filtered peak as its run-time measure; total file runtime is not shown as the decision runtime. The initial back-pressure check is performed first. The exact result `Do not continue run | Ensure Method specifications are met` is returned only when a measured pressure is present and fails its maximum-pressure specification; unavailable pressure is labelled NOT AVAILABLE and does not trigger this exact result. The Dashboard displays peak count, last-peak retention, lowest resolution, and pressure as four individual measurement columns, with each value and its status in the same cell. Suggested (not-yet-run) rows display PENDING in yellow. When peak count is below target, resolution is NOT ASSESSED: its measured value is shown without pass/fail color and without comparison to or reference to the resolution specification. Resolution is assessed against the specification only when peak count meets or exceeds its target. Retention time and pressure pass when at or below their maximum specifications; peak count passes when at or above its target. No near-limit WARNING margin is configured, so none is inferred. The Dashboard uses a wider layout to show more columns at once. Decision, Actions, and the four measurement columns remain fixed on the right, with compact, explicitly stacked widths so scrolling columns pass behind them without overlap. Group No., Trial No., and method-parameter columns before Decision scroll horizontally; columns not in view can be reached with horizontal scrolling. Predicted next-run rows are marked with a blue label and dashed border to distinguish them from uploaded runs. The table initially scrolls to the right so the decision and measurements are immediately visible. The separate Current viewed run panel has been removed.

After the pressure gate passes, an under-target run follows the decision-driven investigation described above; the measured results select the next recommendation. A recorded option must include an observed peak count and retention time. Missing intermediate or minimum predictions pause progression instead of inventing or skipping a value. Pressure failure produces `Do not continue run | Ensure Method specifications are met`; missing pressure remains NOT AVAILABLE under the existing pressure behavior. When a run meets target, the existing runtime/resolution decision branches take over. The Dashboard keeps Decision, Actions, and measurement columns pinned on the right while Group No., Trial No., and parameter columns scroll horizontally without covering the fixed block. Predicted rows are visually distinct from uploaded source runs. Each `Decrease %B by 10%` decision includes an interactive button to Pump → %B → Decision-engine Relationship; that section has a return link to the originating trial. A %B change is 10 percentage points (for example, 70% to 60%), not a relative 10% decrease. The current filename parser recognizes isocratic (`ISO`) methods only; gradient programmes are not parsed or adjusted.

When the peak target is met, the flowchart classifies last-peak retention into three bands: at or below 50% of the maximum, above 50% through the maximum, and above the maximum. For resolution below the SPP Rs floor, it recommends `Increase L (watch BP)` in the first band and `SELECTIVITY` in the other two. For resolution at or above the SPP floor but below the resolution specification, it recommends `Increase L (BP) OR decrease F OR decrease PS (BP) OR SPP` in the first band, `Decrease F OR decrease PS (BP) OR SPP` in the second, and `Decrease PS (BP), then increase F to shorten the run` above the maximum. When resolution meets specification, it recommends `MET. Optionally increase F to shorten the run` in the first two bands and `Increase F to shorten the run` above the maximum. The initial pressure gate still takes precedence, and the below-floor branch follows the workbook's inclusive SPP verdict: resolution equal to the SPP floor is reachable rather than below floor. These branches do not change the existing staged selectivity plan used while investigating runs below the target peak count.

The flowchart's Rs floor comes from the attached AWESOME workbook calculation. Because the current packing type is not inferred, the user must select fully porous or SPP and confirm it before an Rs-floor recommendation is calculated. For seven or more noise-filtered peaks, the workbook estimates current plate count from the Van Deemter equation, computes plate-count headroom from the configured pressure and runtime limits, and calculates the FPP and SPP Rs floors. With fewer than seven peaks, the Rs-floor decision is unavailable rather than treating a placeholder Rs as measured data.

## Efficiency predictions

The `Efficiency Predictions` link on each uploaded run opens the Equipment Guide at Column/Column Oven → Column Length. This is a separate, optional calculator: Mode A explores one allowed change, while Mode B checks a proposed combination entered by the user. It evaluates predicted last-peak retention, pressure, flow bounds, and resolution against the configured limits. Proposed values are never selected automatically. Editing a proposal does not change uploaded measurements, flowchart recommendations, or selectivity history; only the separately required packing-type confirmation supplies the current packing factor used by the Rs-floor calculation.
